### [2026-07-02] NEW: crawlable internal links between locale versions — root-cause fix for the 3,380/3,381 "orphan page" Ahrefs Error
- **New file:** `fullstack_2_3_1/snippets/hreflang-crawlable-links.liquid`.
- **Wired in:** `fullstack_2_3_1/layout/theme.liquid`, one line added after `{% sections 'footer-group' %}`.
- **Root cause investigated and confirmed (via Ahrefs `site-audit-page-explorer`, live `curl`, and code review):** a representative 100-page sample of the "Orphan page (indexable, no incoming internal links)" Error was **100% `/de/products/*` URLs**, all `depth: 0`, `incoming_links: 0`, `page_type: ["Page","Seed"]`, `is_in_sitemap: true` — meaning Ahrefs only knows these pages exist because they're in the XML sitemap, never because it followed a real link to them. Verified why: the theme's language switcher (`snippets/localization-form.liquid`) is Shopify's native **`<select>` + POST form** localization pattern — there is no real `<a href="/de/...">` anywhere in the rendered HTML (confirmed via `curl` + grep on the live homepage: zero `href="/de..."` matches). Search-crawlers cannot follow a form submit. The theme already emits correct `<link rel="alternate" hreflang>` tags (`hreflang-tags.liquid`), which is enough for Google to *discover* and *understand* the locale relationship, but hreflang is metadata, not a link — it passes **zero internal link equity**, and link-graph tools like Ahrefs correctly flag every /de/ (and presumably /en/) page as orphaned since there is no real crawlable path to them from the rest of the site.

### [2026-07-02] FIX: site-wide MerchantReturnPolicy schema.org node was disconnected — likely root cause of the 26,072-URL schema.org validation Notice
- **File:** `fullstack_2_3_1/snippets/site-schema.liquid`.

No new schema type introduced, no visual change, purely a linking-property addition.
- **Confidence note:** this is the strongest single hypothesis given the evidence (site-wide, non-Product-specific, exactly matches an orphaned-node pattern), but Ahrefs' `jsonld_validation_kinds` field returned empty for all sampled URLs (no granular per-field error message available via the API), so this couldn't be 100% confirmed against the literal validator error text. Recommend confirming the Notice count drops after the next crawl post-push.
